# Шаг 7. Один способ запускать расчёт из интерфейса

Часть [плана рефакторинга](../refactoring-roadmap.md). Общие ограничения, порядок работы и проверки описаны
там; здесь только особенности шага. Факты сверены с кодом 2026-11-14 на коммите `575e574`; номера строк
могли сместиться — сверяйте по смыслу. Перед этим шагом должны быть выполнены шаги 3 и 6.

## Зачем

Каждый экран сам пишет одну и ту же цепочку: подождать, пока пользователь перестанет менять входные данные,
отменить прежнюю задачу, запустить новую, не показать устаревший результат, вести признаки «считаем» и
«ошибка». Копии расходятся в деталях, и каждая новая расчётная фича добавляет ещё одну. Отдельно в четырёх
местах повторён выбор «считать сразу в основном потоке или в воркере». После шага всё это живёт в одном
месте, и следующий шаг (очередь воркера) правится там же.

## Что установлено

Запуск по изменению входных данных:

| Где | Задача | Задержка | Пока считается | Защита от устаревшего результата |
| --- | --- | --- | --- | --- |
| `PlacementScreen` — карта варианта | `listenerMap` / `subMap` | 120 мс | карта скрыта | сравнение задач; свой кэш карт на результат подбора |
| `ManualScreen` — карта | `listenerMap` / `subMap` | 350 мс | прежняя карта остаётся, если режим и сабвуфер те же | сравнение задач; отбор по виду карты |
| `VoiceScreen` — карта | `voiceMap` | 250 мс | карта скрыта, если входы другие | сравнение задач и входов по ссылкам |
| `FieldScreen` — поле | `field` | 300 мс | прежняя картинка остаётся | сравнение задач; кэш по ключу входов |
| `FieldScreen` — моды системы | `modes` | нет | список сброшен | отмена при смене входов |
| `ModesScreen`, `ObjectivePicker` | `modes` | уточнить по коду | уточнить | уточнить |
| `MeasurePanel` — сравнение с замером | `compare` | нет | — | отмена при смене входов |
| `useSetupEval` ([useEval.ts](../../src/ui/useEval.ts)) | `evaluate` | нет | прежняя оценка остаётся, признак «считаем» | отмена при смене входов |

Запуск по кнопке: `PlacementScreen` («Подобрать», `optimize`, с прогрессом и проверкой, не изменился ли
проект за время расчёта), `SubPanel` (`integrate`, `subFilters`), `EqPanel` (`evaluate`), `MeasurePanel`
(`calibrate`, результат применяется к последней комнате).

Выбор потока по `isWave(room)`: `useEval.ts`, `EqPanel.tsx`, `MeasurePanel.tsx`, `ManualScreen.tsx` (оценки
сохранённых вариантов). Для прямоугольной комнаты расчёт идёт сразу в основном потоке (3–6 мс на оценку),
для волновой — в воркере.

Действующих гонок при оценке не найдено: «Настройку» защищает перемонтирование панелей по ключу входных
данных ([TuningScreen.tsx](../../src/ui/screens/TuningScreen.tsx)), остальное — отмена и сравнение задач.
Цель шага — убрать повторение, а не исправить ошибку.

## Что должно получиться

- Таблица выше, дополненная и сверенная с кодом, — в спецификации шага как договор о поведении каждого
  места: задержка, что видно во время расчёта, когда результат считается устаревшим, что кэшируется.
- Общий хук (или два: для запуска по изменению входов и для запуска по кнопке), через который работают
  перечисленные места. Хук поддерживает обе существующие манеры: «прежний результат остаётся, пока
  считается новый» и «прежний результат скрывается».
- Выбор «основной поток или воркер» — в одном месте.
- Каждое место после переноса ведёт себя по своей строке договора: те же задержки, те же сообщения, тот же
  порядок и состав задач, уходящих в воркер.
- Место, которое не ложится на общий хук без изменения поведения, остаётся как есть; причина записана в
  спецификации.

## Поведение

Не меняется. Расхождения между местами, перечисленные в таблице, считаются намеренными, пока владелец не
решил иначе: выравнивать задержки и манеру показа в этом шаге нельзя.

## Границы

Не входит: приоритеты и очередь воркера (шаг 8), перенос расчётов прямоугольной комнаты в воркер, изменение
кэшей по содержанию, изменение признака «устарел» у результата подбора, разбиение экранов на части.

## Трудные места

- Сравнение входов идёт по ссылкам на объекты проекта. Хук, который сравнивает по содержимому или
  пересобирает объект входов при каждой отрисовке, изменит число запусков.
- У `ManualScreen` карта зависит от части расстановки (места, настройки сабвуфера, частота раздела), а не
  от всей: переименование варианта пересчёта не вызывает. Список зависимостей каждого места переносится
  как есть.
- Переносить по одному месту за коммит и после каждого запускать e2e и сверку задач (см. «Приёмка», п. 2).
  Так расхождение находится сразу, а не в конце.
- Отмена снимает только задачу, которая ещё не началась; начатая досчитывается, а её ответ отбрасывается
  ([compute.ts](../../src/ui/compute.ts)). Хук не должен обещать больше.

## Приёмка

1. В экранах и компонентах нет прямых вызовов `compute(`; исключения перечислены в спецификации с причиной.
2. Записанная последовательность задач воркера в контрольном сценарии совпадает до и после шага. Сценарий:
   «Расстановка → Вручную» → перетащить слушателя → «Настройка → Сабвуфер» → изменить уровень сабвуфера →
   «Голос» → изменить расстояние до микрофона → «Анализ → Поле 3D». Приём записи — в разделе «Среда и
   приёмы проверки» плана.
3. Unit-тесты общего хука или вынесенной из него чистой логики: задержка, отмена, устаревший результат не
   показывается, обе манеры показа.
4. Сценарии e2e проходят без правок ожиданий.
