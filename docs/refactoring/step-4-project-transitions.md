# Шаг 4. Правила изменения проекта — в слое состояния, с тестами

Часть [плана рефакторинга](../refactoring-roadmap.md). Общие ограничения, порядок работы и проверки описаны
там; здесь только особенности шага. Факты сверены с кодом 2026-11-14 на коммите `575e574`; номера строк
могли сместиться — сверяйте по смыслу.

## Зачем

Почти каждая правка пользователя проходит через одну функцию, которая поддерживает согласованность проекта:
вписывает расстановки в комнату, помечает результат подбора устаревшим, отмечает, что места выбраны. Эта
функция живёт внутри хука интерфейса, поэтому её нельзя проверить unit-тестом — она покрыта только
сквозными сценариями. Ошибка здесь тихо портит данные проекта.

## Что установлено

- [useProject.ts](../../src/ui/useProject.ts) содержит: `fitSetup`, `fitConstraints` (обе не экспортируются)
  и `touch` — применение изменения к проекту. Там же обработчики `onRoom`, `onSources`, `onConstraints`,
  `onSetup`, `onSetups`, `onVoice`, `onPrecision`.
- Ни один файл в `tests` не ссылается на `useProject`, `fitSetup` или `fitConstraints`.
- Два изменения идут мимо `touch`, напрямую через `setProject` ([App.tsx](../../src/ui/App.tsx)): выбор
  варианта подбора (`onSelect`) и замена проекта целиком при открытии, импорте и «Новом проекте»
  (`onReplace`).
- Экраны комнаты передают в `onRoom` дополнительные поля проекта вторым аргументом (`roomReady`, `scanInfo`,
  `current`, `setups`, `constraints`).

## Что должно получиться

- Чистая функция в `src/state` (без хуков, DOM и хранилищ), которая по прежнему проекту и изменению
  возвращает новый проект. В неё переезжают `fitSetup`, `fitConstraints` и тело `touch` без изменения
  логики. Время обновления передаётся параметром, чтобы тесты были детерминированными.
- Именованные переходы для всех изменений проекта, включая два, которые сейчас идут в обход: выбор варианта
  и замена проекта. Их нынешняя семантика сохраняется (см. «Трудные места»).
- В хуке остаются загрузка, отложенное сохранение, сохранение при уходе со страницы и подписка на
  обновление приложения. Набор и сигнатуры того, что хук возвращает экранам, по возможности прежние.
- Unit-тесты, фиксирующие текущие правила:
  - явно переданный `result` (в том числе `null`) важнее пометки «устарел»; иначе при изменении комнаты,
    источников, ограничений и точности результат помечается устаревшим; изменения расстановки, списка
    вариантов, настроек голоса и названия — не помечают;
  - при изменении комнаты, источников, ограничений или текущей расстановки текущая расстановка вписывается
    в комнату; сохранённые варианты — при изменении комнаты или источников;
  - пока места не выбраны, текущая расстановка берёт места по умолчанию для новой комнаты (022);
  - изменение мест пользователем ставит признак «места выбраны»;
  - зона слушателя возвращается к значениям по умолчанию, когда выходит за новую комнату;
  - стандартная точность не записывается в проект.

## Поведение

Не меняется. Это перенос кода с добавлением тестов.

## Границы

Не входит: разбор `storage.ts` и `project.ts` на модули, изменение формата проекта, перенос побочных
действий экранов комнаты (шаг 9), изменение логики сохранения (шаг 2).

## Трудные места

- Сначала перенос без правок, затем тесты на текущее поведение. Если тест показывает правило, которое
  выглядит ошибкой, — не исправлять: описать владельцу в отчёте.
- `onRoom` берёт ограничения из замыкания отрисовки (`project.constraints`), а `touch` работает с
  предыдущим состоянием из `setProject`. При двух быстрых изменениях подряд это разные значения. Перенос
  должен сохранить, какое значение откуда берётся; осознанная смена — только с тестом и записью в отчёте.
- `onSelect` намеренно не меняет `updatedAt` и не помечает результат устаревшим; `onReplace` заменяет
  проект целиком без вписывания. Сохранить.
- `updatedAt` влияет на сравнение дат при импорте того же проекта (024) и на порядок в «Сохранённых».

## Приёмка

1. В `useProject.ts` нет логики согласования проекта — только вызовы функций из `src/state` и работа с
   хранилищем и событиями страницы.
2. В `App.tsx` и экранах нет прямого `setProject` с ручной сборкой проекта.
3. Новые unit-тесты покрывают каждое из перечисленных правил.
4. Существующие unit- и e2e-тесты проходят без правок ожиданий.

## Проверка сверх общей

Сценарии `room-first`, `room-editor`, `projects`, `scan`, `app` — без правок.
