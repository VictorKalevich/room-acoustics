# Шаг 9. Создание и изменение комнаты — именованными операциями в одном модуле

Часть [плана рефакторинга](../refactoring-roadmap.md). Общие ограничения, порядок работы и проверки описаны
там; здесь только особенности шага. Факты сверены с кодом 2026-11-14 на коммите `575e574`; номера строк
могли сместиться — сверяйте по смыслу. Перед этим шагом должны быть выполнены шаги 4 и 6.

## Зачем

Сведения о том, как создаётся комната, лежат в пяти местах, и согласованность между ними держится на
ручных вызовах, разбросанных по экранам. Каждая из фич 019–027 меняла эту область, и ошибки в ней уже
были именно такого рода: одно место обновили, другое забыли. После шага каждое действие пользователя —
одна операция, которая сама делает всё, что с ним связано.

## Что установлено

Где лежит состояние:

| Место | Что хранит |
| --- | --- |
| Проект ([project.ts](../../src/state/project.ts)) | `roomReady`, `scanInfo` с `rotation` и `applied`, `room.source` |
| localStorage, ключ `ra-room-draft-<проект>` ([roomDraft.ts](../../src/ui/roomDraft.ts)) | черновик конструктора: комната, достигнутый шаг, введённые размеры, изменённые поля |
| IndexedDB, хранилище `scans` ([storage.ts](../../src/state/storage.ts)) | сетка скана, распознавание, применённый выбор |
| Локальное состояние компонентов | [ScanPanel.tsx](../../src/ui/screens/room/ScanPanel.tsx) — 18 `useState` и 3 `ref`; [RoomEditor.tsx](../../src/ui/screens/room/RoomEditor.tsx) — 10 `useState` |
| Модульные переменные | просьба открыть поправку границ ([scanFix.ts](../../src/ui/scanFix.ts)); страж ухода со страницы в [navigation.ts](../../src/ui/navigation.ts) |

Где экраны сами выполняют побочные действия:

- `dropRoomDraft` — 6 вызовов: `ProjectsScreen.tsx` (2), `RoomEditor.tsx`, `ScanPanel.tsx` (2),
  `RoomScreen.tsx`.
- `deleteScan` — `ProjectsScreen.tsx`, `RoomScreen.tsx` и внутри `deleteProject`; `saveScan` — `ScanPanel.tsx`.
- Сборка изменения проекта вручную: `ScanPanel` (первое применение скана и поправка границ), `RoomEditor`
  («Сохранить», поворот при проверке скана, переход к поправке границ), `RoomScreen` («Очистить»),
  `ProjectsScreen` (замена и удаление проекта).

Следы прежних ошибок согласованности — в комментариях кода: правка герметичности в конструкторе
заменялась значением проекта (исправлено в 022, `roomDraft.ts`); применённые границы скана не откатывались
вместе с проектом (исправлено в 026, `ScanPanel.tsx`).

## Что должно получиться

- В спецификации шага — таблица «действие пользователя → что происходит с проектом, с черновиком
  конструктора, со сканом на устройстве, куда переходит навигация», выведенная из текущего кода. Действия
  как минимум: первое применение скана; новый скан поверх применённого; поправка границ; «Сохранить» в
  конструкторе; «Не сохранять» и «Сбросить черновик»; поворот при проверке скана; переход к поправке
  границ из шага «Размеры»; «Очистить»; «Новый проект», «Открыть», «Импорт»; удаление сохранённого проекта
  (открытого и другого).
- Один модуль с операцией на каждую строку таблицы. Операция возвращает изменение проекта и сама
  выполняет действия с черновиком и сканом. Чистая часть (каким станет проект) отделена от работы с
  хранилищами, чтобы проверяться unit-тестом.
- Экраны вызывают операции и больше не вызывают `dropRoomDraft`, `deleteScan`, `saveScan` и не собирают
  изменение проекта для этих действий вручную.
- Unit-тесты на каждую строку таблицы с заглушками хранилищ.

## Поведение

Не меняется: те же данные после каждого действия, те же переходы, те же подтверждения. Если таблица
покажет действие, после которого состояние остаётся несогласованным (например, остаётся черновик или скан,
который уже никому не нужен), — не исправлять в рамках шага: описать владельцу с воспроизведением.

## Границы

Не входит: локальное состояние отображения в `ScanPanel` и `RoomEditor` (что раскрыто, что выбрано,
фаза разбора файла) и его перестройка; распознавание скана ([src/scan](../../src/scan)); формат хранения
скана и черновика; порядок шагов конструктора; тексты и вид экранов.

## Трудные места

- Порядок побочных действий сейчас разный в разных местах (например, сначала изменение проекта, потом
  сброс черновика, потом переход, потом запись скана). Перед объединением запишите порядок для каждого
  действия и сохраните его: от него зависит, что прочитает экран при следующей отрисовке.
- Запись скана на устройство идёт асинхронно и её ошибка только пишется в журнал; операция не должна
  начать ждать её или прерываться из-за неё.
- Черновик конструктора кэшируется в памяти по идентификатору проекта (`roomDraft.ts`). Экран читает его
  при монтировании; сброс до или после перемонтирования даёт разный результат.
- `App` читает черновик при каждой отрисовке, пока комната не создана, — для подсказки пункта «Начать» (025).
- Переносите по одному действию за коммит, после каждого — сценарии комнаты и скана.

## Приёмка

1. Поиск по `src/ui` не находит `dropRoomDraft(`, `deleteScan(`, `saveScan(` вне нового модуля.
2. Таблица действий есть в спецификации, и на каждую её строку есть unit-тест.
3. Сценарии `scan`, `room-first`, `room-editor`, `room-controls`, `projects`, `start-menu` проходят без
   правок ожиданий.
4. Содержимое проекта, ключа черновика и хранилища `scans` после каждого действия из таблицы совпадает
   с тем, что было до шага (проверка в e2e по содержимому хранилищ).

## Проверка сверх общей

В отчёте попросить владельца пройти на телефоне после обновления приложения: скан из файла → шаги →
«Сохранить»; поправку границ; «Очистить»; ручную настройку с перерывом и возвратом. Эмуляция этого не
заменяет.
