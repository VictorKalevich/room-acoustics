# Шаг 3. Типизированный обмен с воркером расчётов

Часть [плана рефакторинга](../refactoring-roadmap.md). Общие ограничения, порядок работы и проверки описаны
там; здесь только особенности шага. Факты сверены с кодом 2026-11-14 на коммите `575e574`; номера строк
могли сместиться — сверяйте по смыслу.

## Зачем

Тяжёлые расчёты идут в фоновом потоке. Интерфейс и воркер договариваются о составе входных данных и типе
результата только на словах: компилятор эту договорённость не проверяет. Опечатка в имени поля или
изменённая сигнатура функции ядра проходит сборку и проявляется уже неверным расчётом или ошибкой на
устройстве. Этот файл обмена меняется почти в каждой расчётной фиче (9 из 45 коммитов).

## Что установлено

- [compute.ts](../../src/ui/compute.ts): `compute<T>(type, payload: unknown, onProgress)`. Тип результата `T`
  назначает вызывающий код, связи с `type` нет.
- [compute.worker.ts](../../src/workers/compute.worker.ts): `interface Job { id; type: string; payload: any }`
  и `switch` по строке; поля берутся из `p.room`, `p.setup`, `p.ppo` и т. д. без проверки типов.
- 11 видов задач: `optimize`, `listenerMap`, `subMap`, `integrate`, `calibrate`, `compare`, `evaluate`,
  `modes`, `field`, `subFilters`, `voiceMap`.
- 14 мест вызова: `useEval.ts`, `ObjectivePicker.tsx`, `FieldScreen.tsx` (2), `ManualScreen.tsx`,
  `MeasurePanel.tsx` (2), `ModesScreen.tsx`, `PlacementScreen.tsx` (2), `EqPanel.tsx`, `SubPanel.tsx` (2),
  `VoiceScreen.tsx`.
- Диспетчер воркера не покрыт unit-тестами: модуль при загрузке обращается к `self`.
- Второй воркер, [detect.worker.ts](../../src/workers/detect.worker.ts), вызывается из
  [ScanPanel.tsx](../../src/ui/screens/room/ScanPanel.tsx) через `runWorker<T>` с тем же недостатком:
  тип ответа назначает вызывающий код.

## Что должно получиться

- Одна таблица типов «вид задачи → входные данные → результат», общая для интерфейса и воркера. Входные
  типы выводятся из сигнатур функций ядра, а не описываются второй раз вручную.
- `compute` принимает вид задачи и проверенные компилятором входные данные и возвращает задачу с типом
  результата, выведенным из вида задачи. В местах вызова явный тип результата больше не нужен.
- В воркере — таблица обработчиков, которую компилятор проверяет на полноту: добавление вида задачи без
  обработчика или с другим набором полей не собирается.
- Обработчики лежат в модуле, который можно импортировать в тестах без воркера; файл воркера остаётся
  тонкой обвязкой (очередь, прогресс, передача буферов, ошибки).
- Тот же приём для `detect.worker` и `runWorker` в `ScanPanel`: типы запроса и ответа из одного места.
  Логику панели скана при этом не трогать — она относится к шагу 9.

## Поведение

Не меняется. На проводе всё остаётся прежним: те же строки `type`, те же имена полей, та же копия данных
через JSON перед отправкой, та же передача буферов для `field` и `voiceMap`, та же очередь и отмена,
те же сообщения об ошибках и записи в журнале.

## Границы

Не входит: очередь и приоритеты (шаг 8), общий хук запуска расчёта (шаг 7), перенос расчётов между потоками,
изменение функций ядра и их сигнатур.

## Трудные места

- Копия через `JSON.parse(JSON.stringify(payload))` отбрасывает `undefined` и не переносит типизированные
  массивы. Типы входных данных не должны обещать больше, чем доходит до воркера.
- `optimize` и `field` передают объект целиком в функцию ядра, остальные задачи раскладывают поля по
  аргументам. Не унифицируйте формат на проводе ради красоты — это изменит поведение при рассинхроне версий
  страницы и воркера после обновления приложения.
- Результаты `field` и `voiceMap` содержат типизированные массивы и передаются с передачей владения
  буферами; это должно остаться.

## Приёмка

1. Неверное имя поля, пропущенное обязательное поле или несоответствие типа результата в месте вызова —
   ошибка компиляции. Это закреплено проверкой типов в тестах (строки с `@ts-expect-error`, которые
   проверяет `tsc --noEmit` из `npm run build`).
2. В `compute.ts`, файлах воркеров и новом модуле обработчиков нет `any`, кроме приведения списка
   передаваемых буферов, если без него не обойтись.
3. Unit-тест прогоняет каждый из 11 видов задач через таблицу обработчиков на небольшой комнате и
   сравнивает результат с прямым вызовом функции ядра.
4. Последовательность задач, уходящих в воркер в сценарии «Расстановка вручную → Настройка → правка уровня
   сабвуфера», до и после шага одинакова (приём записи — в разделе «Среда и приёмы проверки» плана).

## Проверка сверх общей

Сценарии e2e, затрагивающие расчёты (`app`, `precision`, `voice-goals`, `scan`), проходят без правок.
