# Шаг 2. Сбой чтения не стирает рабочий проект

Часть [плана рефакторинга](../refactoring-roadmap.md). Общие ограничения, порядок работы и проверки описаны
там; здесь только особенности шага. Факты сверены с кодом 2026-11-14 на коммите `575e574`; номера строк
могли сместиться — сверяйте по смыслу.

## Зачем

Рабочий проект («черновик») хранится на устройстве и восстанавливается при запуске. Если при запуске он
не прочитался, приложение молча открывает новый пустой проект и вскоре записывает его на место прежнего.
Пользователь теряет всё, что не сохранил в «Проектах» и не экспортировал.

## Что установлено

- `loadDraft` в [storage.ts](../../src/state/storage.ts) превращает ошибку чтения IndexedDB в «черновика
  нет»: `tx(...).catch(() => undefined)`. Проверено скриптом: при `indexedDB.open`, который завершается
  ошибкой, `loadDraft()` возвращает `undefined`, а не отклоняется.
- [useProject.ts](../../src/ui/useProject.ts): начальное состояние — `newProject()`; после `loadDraft`
  выставляется `ready`, и эффект автосохранения через 300 мс записывает текущий проект как черновик —
  даже если пользователь ничего не менял. Это следует из кода; на устройстве не воспроизводилось.
- Если черновик прочитан, но не прошёл `normalizeProject`, его копия пишется под ключ `draft-failed`
  (один на всё устройство), ошибка уходит в журнал, а приложение открывает новый проект. Открыть или
  выгрузить `draft-failed` из интерфейса нельзя.
- `open()` в [storage.ts](../../src/state/storage.ts) создаёт новое соединение с базой на каждую операцию
  и не закрывает его; обработчика `versionchange` нет. При следующей смене версии базы открытая старая
  вкладка или установленное приложение заблокирует новую версию («Хранилище занято другой вкладкой…»),
  и сработает сценарий из первого пункта.

Насколько часто чтение IndexedDB срывается на iPhone, не измерялось. Известны сбои соединения в Safari
после возврата из фона; вероятность считаем низкой, последствие — потерей данных.

## Что должно получиться

- Приложение различает три исхода запуска: черновик открыт; черновика нет (первый запуск); черновик
  прочитать или открыть не удалось.
- В третьем случае прежний черновик на устройстве не перезаписывается, пока пользователь явно не выбрал
  продолжить без него. Перед сообщением чтение повторяется несколько раз с короткой паузой: такие сбои
  обычно кратковременны.
- Пользователь видит, что произошло, и может действовать:

| Случай | Текст | Действия |
| --- | --- | --- |
| Хранилище не читается | «Не удалось открыть сохранённый проект». «Данные на устройстве не тронуты.» | «Повторить», «Начать новый проект» (с подтверждением, что прежний рабочий проект будет заменён) |
| Черновик не прошёл проверку | «Сохранённый проект повреждён» и причина из проверки | «Сохранить копию в файл», «Начать новый проект» |

  Формулировки — предложение; владелец согласовал их отправкой команды на шаг, иные указания в команде
  важнее. Сообщение строится из существующих элементов дизайн-системы (как в шаге 1, если он выполнен —
  тем же компонентом) и вносится в реестр, каталог и документацию.
- Соединение с базой одно на вкладку; при `versionchange` оно закрывается, при следующей операции
  открывается заново. Запросы и их результаты не меняются.

## Поведение

Меняется только при сбое чтения или проверки черновика. Обычный запуск, автосохранение через 300 мс,
сохранение при уходе со страницы (`ra-draft-pending`) и формат данных остаются прежними.

## Границы

Не входит: одновременная работа в двух вкладках (сейчас побеждает последняя запись), смена схемы или версии
базы, перенос хранения в другое место, разбор `storage.ts` на модули.

## Трудные места

- Запись `ra-draft-pending` в localStorage читается независимо от IndexedDB и важнее черновика. Если она
  есть и исправна, сбой IndexedDB не должен мешать открыть проект из неё.
- «Не перезаписывать» касается всех путей записи черновика: отложенного сохранения, сохранения при уходе
  со страницы и сохранения перед обновлением приложения (`setBeforeReload` в
  [updates.ts](../../src/ui/updates.ts)).
- Пока показывается сообщение о сбое, остальной интерфейс не должен работать с пустым проектом так, будто
  он настоящий.
- В проекте нет тестовой реализации IndexedDB, тесты идут в среде `node`. Для unit-тестов достаточно
  небольшой заглушки `globalThis.indexedDB` в самом тесте; новая зависимость допустима, только если без неё
  не обойтись, с обоснованием в отчёте. В e2e сбой задаётся через `page.addInitScript`: подменить
  `IDBFactory.prototype.open` так, чтобы первые N вызовов завершались ошибкой.

## Приёмка

1. При сбое чтения черновик на устройстве остаётся прежним: после «Повторить» (когда хранилище снова
   доступно) открывается тот же проект с теми же данными.
2. Кратковременный сбой (первые одна–две попытки) пользователь не замечает: проект открывается.
3. «Начать новый проект» спрашивает подтверждение и только после него заменяет черновик.
4. Черновик, не прошедший проверку, выгружается в файл кнопкой из сообщения.
5. Обычный запуск без сбоев: существующие сценарии e2e проходят без правок ожиданий.
6. После закрытия соединения по `versionchange` следующая операция с хранилищем выполняется.

## Проверка сверх общей

- Unit: исходы `loadDraft` (есть, нет, ошибка чтения, не прошёл проверку, есть `ra-draft-pending`);
  повторное открытие соединения.
- e2e: сбой первых N открытий базы — проект открывается; постоянный сбой — сообщение, затем «Повторить»
  после снятия сбоя; содержимое черновика в IndexedDB до и после совпадает.
