# 031 — Правила изменения проекта в слое состояния

Статус: реализовано 2026-11-15. Основание: [D24](../decisions.md), шаг 4
[плана рефакторинга](../../docs/refactoring-roadmap.md) ([описание шага](../../docs/refactoring/step-4-project-transitions.md)).
Переносит правила согласования проекта из хука интерфейса в `src/state` и закрепляет их unit-тестами. Правила прежние,
из них в коде отмечены этапами места по умолчанию и признак «места выбраны» ([022](../022-room-flow/spec.md)) и
точность ([026](../026-calc-precision/spec.md)). Поведение, формат и версия файла проекта, логика сохранения
([029](../029-draft-safety/spec.md)) и ядро не меняются.

## Задача владельца

Команда владельца на шаг 4 плана: функция, через которую проходит почти каждая правка пользователя и которая держит
проект согласованным (вписывает расстановки в комнату, помечает результат подбора устаревшим, отмечает, что места
выбраны), должна жить в слое состояния и проверяться unit-тестами, а не только сквозными сценариями. Ошибка в ней тихо
портит данные проекта.

## Что было (сверено с кодом 2026-11-15, коммит `e2b8357`)

- `src/ui/useProject.ts`: `fitSetup` и `fitConstraints` (не экспортируются) и `touch(patch, invalidate = true)` —
  применение изменения внутри `setProject((prev) => …)` со временем `new Date().toISOString()`. Обработчики:
  - `onRoom(room, extra = {})` → `touch({ ...extra, room, constraints: fitConstraints(extra.constraints ?? project.constraints, room) })`
    — ограничения берутся из проекта, с которым отрисован хук (замыкание), а не из `prev`;
  - `onSources`, `onConstraints` → `touch({ sources })`, `touch({ constraints })`;
  - `onSetup(current)` → `touch((prev) => ({ current: markPlaced(prev.current, current) }), false)`;
  - `onSetups`, `onVoice` → `touch({ setups }, false)`, `touch({ voice }, false)`;
  - `onPrecision(precision)` → `touch({ precision: precision === 'standard' ? undefined : precision })`.
- Хук возвращал `setProject` и `touch`. `App.tsx` пользовался ими напрямую: `onResult` автоподбора —
  `touch({ result, selectedIndex }, false)`, `onRename` «Проектов» — `touch({ name }, false)`, `onSelect` автоподбора —
  `setProject((p) => ({ ...p, selectedIndex }))` (без `updatedAt` и пометки «устарел»), `onReplace` «Проектов» —
  `setProject(p)` (открытие, импорт, «Новый проект»; без вписывания). В самом хуке — `setProject(d)` после загрузки
  черновика и `setProject(newProject())` в «Начать новый проект» (029).
- Экраны комнаты передают в `onRoom` поля проекта вторым аргументом: `RoomScreen` (`clearedRoom`), `RoomEditor`
  (`roomReady`, `scanInfo`), `ScanPanel` (`scanInfo`, `constraints`, `current`, `setups`, `roomReady`, результат
  `clearedRoom`).
- Ни один файл в `tests` не ссылался на `useProject`, `fitSetup` или `fitConstraints`.

## Требования

### А. Переходы проекта

- FR-3101: модуль `src/state/transitions.ts` — без хуков, DOM, хранилищ и системного времени. В него переезжают без
  изменения логики `fitSetup`, `fitConstraints` и тело `touch` — функция `applyPatch(prev, patch, now, invalidate = true)`;
  время изменения `now` (ISO-строка) — параметр.
- FR-3102: переход — `Transition = (prev: Project, now: string) => Project`. Каждое изменение проекта из интерфейса —
  именованный переход:

  | Переход | Обработчик | Результат подбора | Вписывание в комнату | `updatedAt` |
  | --- | --- | --- | --- | --- |
  | `changeRoom(room, extra, shown)` | `onRoom` | заданный в `extra`, иначе устарел | текущая и сохранённые | `now` |
  | `changeSources(sources)` | `onSources` | устарел | текущая и сохранённые | `now` |
  | `changeConstraints(constraints)` | `onConstraints` | устарел | текущая | `now` |
  | `changeSetup(current)` | `onSetup` | прежний | текущая | `now` |
  | `changeSetups(setups)` | `onSetups` | прежний | — | `now` |
  | `changeVoice(voice)` | `onVoice` | прежний | — | `now` |
  | `changePrecision(precision)` | `onPrecision` | устарел | — | `now` |
  | `setResult(result, selectedIndex)` | `onResult` | заданный | — | `now` |
  | `renameProject(name)` | `onRename` | прежний | — | `now` |
  | `selectVariant(selectedIndex)` | `onSelect` | прежний | — | прежний |
  | `replaceProject(project)` | `onReplace`, загрузка черновика, «Начать новый проект» | из нового проекта | — | из нового проекта |

  «Устарел» — `{ ...prev.result, stale: true }`, если результат был; без результата остаётся `null`.
- FR-3103: значения берутся оттуда же, откуда раньше. `changeRoom` берёт ограничения из `extra.constraints`, а без них —
  из `shown`: хук передаёт ограничения проекта, с которым он отрисован, а не `prev` из `setProject`. При двух изменениях
  подряд до новой отрисовки это разные значения; правило сохранено и закреплено тестом. `changeSetup` сравнивает новые
  места с `prev.current`. Остальное берётся из `prev`.

### Б. Хук и экраны

- FR-3104: в `useProject` остаются загрузка черновика, «Повторить», «Начать новый проект», отложенное сохранение,
  сохранение при уходе со страницы и подписка на обновление приложения (`setBeforeReload`). Все изменения проекта
  проходят через `apply(transition)` — `setProject((prev) => transition(prev, new Date().toISOString()))`; правил
  согласования проекта в хуке нет.
- FR-3105: хук возвращает прежние `project`, `ready`, `problem`, `retry`, `startNew`, `onRoom`, `onSources`,
  `onConstraints`, `onSetup`, `onSetups`, `onVoice`, `onPrecision` с прежними сигнатурами; вместо `setProject` и `touch`
  — `onResult`, `onRename`, `onSelect`, `onReplace`. Свойства экранов не меняются.
- FR-3106: в `App.tsx` и экранах нет `setProject` и `touch`; изменения проекта — только через обработчики хука.

### В. Правила, закреплённые unit-тестами

- FR-3107: `tests/state/transitions.test.ts` фиксирует:
  1. явно переданный `result` (в том числе `null`) важнее пометки «устарел»; иначе при изменении комнаты, источников,
     ограничений и точности результат помечается устаревшим; изменения расстановки, списка вариантов, настроек голоса
     и названия — не помечают;
  2. при изменении комнаты, источников, ограничений или текущей расстановки текущая расстановка вписывается в комнату;
     сохранённые варианты — при изменении комнаты или источников;
  3. пока места не выбраны, текущая расстановка берёт места по умолчанию для новой комнаты (022);
  4. изменение мест пользователем ставит признак «места выбраны»;
  5. зона слушателя возвращается к значениям по умолчанию, когда выходит за новую комнату;
  6. стандартная точность не записывается в проект;
  7. `updatedAt` — время перехода, кроме выбора варианта и замены проекта; замена проекта не вписывает расстановки;
  8. ограничения для `changeRoom` — из `extra` или из отрисовки (FR-3103); прежний проект переходы не меняют.

### Г. Без изменений

- FR-3108: видимое поведение, формат и версия файла проекта, логика сохранения черновика (029), побочные действия
  экранов комнаты (шаг 9 плана), `src/state/project.ts` и `storage.ts` (их разбор — вне плана), ядро.

## Приёмка

1. В `useProject.ts` нет логики согласования проекта — только вызовы функций из `src/state` и работа с хранилищем и
   событиями страницы.
2. В `App.tsx` и экранах нет прямого `setProject` с ручной сборкой проекта.
3. Новые unit-тесты покрывают каждое из перечисленных правил.
4. Существующие unit- и e2e-тесты проходят без правок ожиданий; сценарии `room-first`, `room-editor`, `projects`,
   `scan`, `app` — без правок.

## Реализация и проверка

Реализовано 2026-11-15 на ветке `refactor/step-4`, коммиты `403a7b6`…`5cc91e3` (и сверка документации).

- Переходы (`src/state/transitions.ts`): `Transition`, `fitSetup`, `fitConstraints`, `applyPatch` (прежнее тело `touch`,
  время — параметр `now`), `changeRoom`, `changeSources`, `changeConstraints`, `changeSetup`, `changeSetups`,
  `changeVoice`, `changePrecision`, `setResult`, `renameProject`, `selectVariant`, `replaceProject` — FR-3101–FR-3103.
  Модуль зависит только от `src/state/project.ts`, `src/state/variant.ts` и ядра (`clampToRoom`, `baselinePositions`).
- Хук: `apply(transition)` — `setProject((prev) => transition(prev, new Date().toISOString()))`; через него идут все
  обработчики, загрузка черновика и «Начать новый проект». `onRoom` передаёт в `changeRoom` ограничения проекта этой
  отрисовки, как раньше. Хук возвращает `onResult`, `onRename`, `onSelect`, `onReplace` вместо `setProject` и `touch`;
  `App.tsx` передаёт их экранам без обёрток, кроме прежнего перехода на «Комнату» после `onReplace` — FR-3104–FR-3106.
- Тесты (`tests/state/transitions.test.ts`, 26, новых зависимостей нет): прежний проект в каждом тесте глубоко заморожен
  и сверяется до и после перехода; время изменения задано тестом — FR-3107.

Проверка 2026-11-15 (Windows, сквозные сценарии — эмуляция iPhone в установленном Chrome):

- Базовая линия на `main` (`e2b8357`) до изменений: 402 unit-теста в 52 файлах, lint с `design:check` и сборка проходят,
  e2e — 90 сценариев с первого прогона (55,2 с).
- `npm test`: 428 unit-тестов в 53 файлах прошли (26 новых). `npm run lint` с `design:check`: без замечаний.
  `npm run build` (с `tsc --noEmit`): проходит; основной чанк интерфейса 481,87 → 482,17 кБ (gzip 156,19 → 156,26 кБ) —
  именованные переходы.
- e2e на `5cc91e3`: первый прогон — ни один сценарий не прошёл, в выводе 115 повторов клика, что похоже на известную
  гонку фокуса в подготовке `room.setup.ts` (шаг 6 плана); имя упавшего сценария в сохранённой части вывода не
  осталось. Второй прогон — 90 сценариев (54,0 с), третий — 90 сценариев с первой попытки, включая `room.setup.ts`
  (54,2 с). Файлы e2e не менялись.
- Сверка с прежним кодом (T3104): прежний хук (`a01b41d`) с прежними обёртками `App.tsx` и новый хук запускались на
  подменённых `preact/hooks` (отрисовка — вызов хука, обновление применяется к предыдущему состоянию по порядку), время
  и `randomUUID` заданы. 3000 случайных последовательностей по 15 изменений от четырёх начальных проектов (новый; с
  результатом, выбранными местами, вариантами, точностью и голосом; комната 3 × 2,5 м с двумя сабвуферами; скан без
  созданной комнаты), все 12 обработчиков вместе с «Начать новый проект»; 18 069 из 45 000 изменений пришли без отрисовки
  после предыдущего. После каждого изменения проекты совпадают целиком (с ключами со значением `undefined`), совпадает
  и то, заменён ли объект проекта. Сверка различает подмену: если `onRoom` берёт ограничения из предыдущего состояния,
  расходятся 627 из 3000 последовательностей; если выбор варианта меняет `updatedAt` — 551 из 1000. Скрипты — во
  временном каталоге, в репозиторий не входят.
- Приёмка: 1 — поиск по `useProject.ts` не находит `fitSetup`, `fitConstraints`, `markPlaced`, `clampToRoom`,
  `baselinePositions`, `syncSetup`, `defaultConstraints`, `updatedAt` и сборку проекта; `setProject` — только в
  `useState` и `apply`. 2 — в `App.tsx` и `src/ui/screens` нет ни `setProject`, ни `touch`. 3 — 26 тестов по
  правилам 1–8 из FR-3107. Каждая из 20 мутаций `transitions.ts`, нарушающих по одному правилу (явный `null` не важнее
  пометки, пометка выключена по умолчанию, расстановка помечает устаревшим, текущая расстановка не вписывается, варианты
  вписываются при ограничениях или не вписываются, места по умолчанию не берутся / берутся для выбранных мест / для
  вариантов, без `markPlaced`, зона не возвращается, начало зоны у стены допустимо, стандартная точность пишется, выбор
  варианта меняет время, изменение не ставит время, замена проекта вписывает, ограничения из предыдущего состояния или
  не из `extra`, сравнение мест не с `prev.current`, прежний проект меняется), роняет тесты. 4 — существующие unit-тесты
  и 90 сценариев e2e, в том числе `room-first`, `room-editor`, `projects`, `scan`, `app`, проходят без правок.

Не проверялось: движок Safari (WebKit) и физический iPhone — эмуляция в Chrome их не заменяет. Поведение не должно
меняться; после обновления приложения на телефоне стоит пройти обычные правки: размеры и материалы комнаты, места
колонок, подбор и выбор варианта, переименование, открытие проекта из «Проектов».

Замечено, не исправлено:

- `onRoom` без ограничений в `extra` берёт их из проекта той отрисовки, из которой пришло изменение (FR-3103). Если до
  новой отрисовки ограничения успели измениться, `onRoom` вернёт прежние: тест «комната без ограничений в extra берёт
  ограничения отрисовки» это фиксирует. Сейчас такого пути нет: `onConstraints` получает только «Расстановка», где нет
  `onRoom`, а обработчиков с двумя вызовами `onRoom` подряд поиск не находит. Отдельные действия пользователя разделены
  отрисовкой. `ScanPanel` так же собирает `constraints` из проекта отрисовки (область шага 9). Смена правила — отдельное
  решение; по просьбе владельца 2026-11-15 записано в [отложенные задачи](../deferred.md) («Исправить позже: замечено
  при рефакторинге»).
