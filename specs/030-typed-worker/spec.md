# 030 — Типизированный обмен с воркерами расчётов и скана

Статус: реализовано 2026-11-14. Основание: [D23](../decisions.md), шаг 3
[плана рефакторинга](../../docs/refactoring-roadmap.md) ([описание шага](../../docs/refactoring/step-3-typed-worker.md)).
Уточняет, как интерфейс обращается к воркеру расчётов (постоянный воркер с очередью — [003](../003-openings-wave-model/spec.md),
задачи — 002, 004, 005, 013, 026) и к воркеру распознавания скана ([001](../001-room-acoustics-mvp/spec.md), 020).
Функции ядра и их сигнатуры, формат и версия файла проекта, сообщения на проводе и видимое поведение не меняются.

## Задача владельца

Команда владельца на шаг 3 плана: договорённость интерфейса и воркеров о составе входных данных и типе результата
должен проверять компилятор, а не держать в голове разработчик. Опечатка в имени поля или изменённая сигнатура
функции ядра должна останавливать сборку, а не проявляться неверным расчётом на устройстве.

## Что было (сверено с кодом 2026-11-14, коммит `6f3327e`)

- `compute<T>(type, payload: unknown, onProgress)` (`src/ui/compute.ts`): тип результата `T` назначает вызывающий
  код, связи с `type` нет; входные данные не проверяются.
- `compute.worker.ts`: `interface Job { id; type: string; payload: any }` и `switch` по строке; поля берутся из
  `p.room`, `p.setup`, `p.ppo` и т. д. без проверки типов; список передаваемых буферов приводится `as any`.
- 11 видов задач (`optimize`, `listenerMap`, `subMap`, `integrate`, `calibrate`, `compare`, `evaluate`, `modes`,
  `field`, `subFilters`, `voiceMap`) и 14 мест вызова: `useEval.ts`, `ObjectivePicker.tsx`, `FieldScreen.tsx` (2),
  `ManualScreen.tsx`, `MeasurePanel.tsx` (2), `ModesScreen.tsx`, `PlacementScreen.tsx` (2), `EqPanel.tsx`,
  `SubPanel.tsx` (2), `VoiceScreen.tsx`.
- Диспетчер воркера не покрыт unit-тестами: модуль при загрузке обращается к `self`.
- `detect.worker.ts` вызывается из `ScanPanel.tsx` через `runWorker<T>(msg: Record<string, unknown>, …)`: тип ответа
  назначает вызывающий код; буфер контура передаётся `as any`.

## Требования

### А. Таблица задач

- FR-3001: одна таблица типов «вид задачи → входные данные → результат» (`ComputeJobs`, `src/workers/computeJobs.ts`),
  общая для интерфейса и воркера. Типы входных данных и результата выводятся из сигнатур функций ядра
  (`Parameters`, `ReturnType`); вручную записаны только имена полей на проводе. Модуль содержит только типы:
  интерфейс подключает его через `import type`, и функции ядра в сборку интерфейса через него не попадают.
- FR-3002: виды задач и поля на проводе прежние:

  | Вид | Поля | Вызов ядра |
  | --- | --- | --- |
  | `optimize` | `room`, `sources`, `constraints`, `precision?` | `optimizePlacement(p, progress)` — объект целиком |
  | `listenerMap` | `room`, `sources`, `constraints`, `setup`, `ppo?` | `listenerHeatmap(…, { ppo, onProgress })` |
  | `subMap` | то же и `subId` | `subHeatmap(…, subId, { ppo, onProgress })` |
  | `integrate` | `room`, `sources`, `constraints`, `setup`, `ppo?` | `optimizeSubs(…, { ppo })` |
  | `calibrate`, `compare` | `room`, `sources`, `constraints`, `setup`, `measurement` | `calibrate(…)`, `compareMeasurement(…)` |
  | `evaluate` | `room`, `sources`, `constraints`, `setup`, `ppo?` | `evaluateSetup(…, { ppo, onProgress })` |
  | `modes` | `room`, `fMax?` | `waveSystemModes(room, fMax, progress)` |
  | `field` | `room`, `sources`, `setup`, `freqs`, `kind`, `modes?` | `computeField(p, progress)` — объект целиком |
  | `subFilters` | `room`, `sources`, `constraints`, `setup`, `ppo?` | `optimizeSubFilters(…, { ppo })` |
  | `voiceMap` | `room`, `settings`, `goal?`, `precision?` | `voiceMap(room, settings, progress, goal, precision)` |

  Формат на проводе не унифицируется: `optimize` и `field` по-прежнему передают объект в ядро целиком, остальные
  раскладывают поля по аргументам. Лишнее поле, которое место вызова отправляет и раньше (`subId` у `listenerMap`
  в ручном режиме и карте автоподбора: вид выбирается по условию), остаётся.
- FR-3003: типы входных данных не обещают больше, чем доходит до воркера после JSON-копии: проверка `JsonSafe` в
  конце `computeJobs.ts` не пропускает типизированные массивы, буферы, функции, даты, `RegExp`, `Map`, `Set`,
  `bigint`, `symbol` и `undefined` в элементах массива — ошибка компиляции с названием вида задачи. NaN и
  бесконечность копия, как и раньше, превращает в `null`; тип `number` этого не различает.

### Б. Интерфейс

- FR-3004: `compute(type, payload, onProgress?)` принимает вид задачи K и входные данные `ComputePayload<K>` и
  возвращает `ComputeJob<ComputeResult<K>>`. Явный тип результата в 14 местах вызова не указывается (прежняя форма
  `compute<T>(…)` не собирается). Неизвестный вид, неверное имя поля, пропущенное обязательное поле, поле другого
  типа и несоответствие результата в месте вызова — ошибка компиляции.
- FR-3005: на проводе и в поведении прежнее: сообщение `{ id, type, payload }` с JSON-копией входных данных, отмена
  `{ cancel: id }` ещё не начатой задачи, ответы `progress` / `done` / `error` (с `stack`), запись ошибки в журнал
  (`logError('worker', …, type)`), отклонение всех задач и новый воркер после сбоя воркера.

### В. Воркер расчётов

- FR-3006: обработчики — таблица `computeHandlers` в `src/workers/computeHandlers.ts` с типом
  `{ [K in ComputeType]: ComputeHandler<K> }`: вид задачи без обработчика, лишний обработчик, обращение к полю,
  которого нет во входных данных, и результат другого типа — ошибка компиляции. Модуль не обращается к `self` и
  импортируется в тестах без воркера.
- FR-3007: `compute.worker.ts` — тонкая обвязка: очередь, ход расчёта не чаще раза в 100 мс (и при 1), передача
  буферов результата `field` (`energy`, `mask`) и `voiceMap` (`scores`, `facing`, `allowed`), остальные результаты —
  с пустым списком, ошибки с текстом и стеком. Неизвестный вид задачи (сообщение от страницы другой версии)
  проверяется при выполнении: прежняя ошибка «Неизвестная задача …», в том числе для имён свойств объекта
  (`toString` и т. п.).
- FR-3008: в `compute.ts`, файлах воркеров и модулях договора и обработчиков нет `any`. Списки передаваемых буферов
  приводятся к `ArrayBuffer` (буферы созданы как `ArrayBuffer`, а типы ядра объявляют `ArrayBufferLike`); `self`
  воркера приводится к описанию из договора — что воркер принимает и что отправляет.

### Г. Воркер скана

- FR-3009: запросы и ответы воркера распознавания — в `src/workers/detectJobs.ts`: распознавание (`DetectRequest`,
  на проводе без `type`, как раньше) с ответом `{ ok: true, result, layout }`, разбор для выбранных границ
  (`LayoutRequest`, `type: 'layout'`) с ответом `{ ok: true, layout }`, ошибка `{ ok: false, error }`. Поля выводятся
  из сигнатур `detectRoom` и `analyzeLayout`. `runWorker` в `ScanPanel` имеет тип `RunScanWorker` (перегрузки
  «запрос → ответ»): тип ответа выводится из вида запроса, явный тип в двух местах вызова не указывается, лишние и
  пропущенные поля — ошибка компиляции. Логика панели скана прежняя (шаг 9 плана).

### Д. Без изменений

- FR-3010: функции ядра и их сигнатуры, формат и версия файла проекта, очередь и приоритеты (шаг 8), общий хук
  запуска расчёта (шаг 7), распределение расчётов между основным потоком и воркером, тексты ошибок и записи журнала
  остаются прежними.

## Приёмка

1. Неверное имя поля, пропущенное обязательное поле или несоответствие типа результата в месте вызова — ошибка
   компиляции; это закреплено строками с `@ts-expect-error`, которые проверяет `tsc --noEmit` из `npm run build`.
2. В `compute.ts`, файлах воркеров и новых модулях нет `any`, кроме приведения списка передаваемых буферов, если без
   него не обойтись.
3. Unit-тест прогоняет каждый из 11 видов задач через таблицу обработчиков на небольшой комнате и сравнивает
   результат с прямым вызовом функции ядра.
4. Последовательность задач, уходящих в воркер в сценарии «Расстановка вручную → Настройка → правка уровня
   сабвуфера», до и после шага одинакова.
5. Сценарии e2e, затрагивающие расчёты (`app`, `precision`, `voice-goals`, `scan`), проходят без правок.

## Реализация и проверка

Реализовано 2026-11-14 на ветке `refactor/step-3`, коммиты `656eb72`…`3a4b1fc` (и сверка документации).

- Договор (`src/workers/computeJobs.ts`): `ComputeJobs`, `ComputeType`, `ComputePayload<K>`, `ComputeResult<K>`, сообщения
  `ComputeRequest`, `ComputeCancel`, `ComputeReply`; проверка `JsonSafe` / `PayloadsSurviveJson` — FR-3001–FR-3003.
- Интерфейс: `compute<K>(type, payload, onProgress?)` в `src/ui/compute.ts` отправляет сообщения через `send` с типом
  `ComputeMessage`, JSON-копия — `jsonCopy`; 14 мест вызова — без явного типа (`ComputeJob<T>` в ссылках на задачу
  остаётся с типом результата) — FR-3004, FR-3005.
- Воркер: `computeHandlers` и `runHandler` (`src/workers/computeHandlers.ts`), `compute.worker.ts` — очередь, ход,
  таблица передаваемых буферов `transfers`, ошибки — FR-3006–FR-3008.
- Скан: `src/workers/detectJobs.ts`, `detect.worker.ts`, `runWorker` в `ScanPanel.tsx` — FR-3009. Обобщённая реализация
  `runWorker` к перегрузкам не приводится (TypeScript сравнивает её с перегрузками, стирая параметр типа), поэтому она
  принимает любой запрос и один раз приводится к `RunScanWorker` — так же, как раньше приводился ответ.
- Оставшиеся приведения — только на границе с данными из сообщения: результат по `id` задачи в `compute.ts`,
  `JSON.parse` в `jsonCopy`, `self` воркеров, буферы к `ArrayBuffer`, прежнее `err as Error`.
- Тесты (`tests/workers/`, новых зависимостей нет): `jobCases.ts` — задача каждого вида на комнате 4 × 3 × 2,7 м со
  значениями, отличными от умолчаний ядра (`ppo`, `precision`, `goal`, `fMax`), чтобы потерю поля было видно;
  `computeHandlers.test.ts` — таблица против прямого вызова ядра после JSON-копии (приёмка 3);
  `compute.worker.test.ts` и `detect.worker.test.ts` — воркеры целиком с подменённым `self`;
  `computeTypes.test.ts` — выведенные типы и 18 строк с `@ts-expect-error` (приёмка 1).

Проверка 2026-11-14 (Windows, сквозные сценарии — эмуляция iPhone в установленном Chrome):

- Базовая линия на `main` (`e25c7ef`; следующий коммит `6f3327e` менял только план) до изменений: 368 unit-тестов в
  48 файлах, lint с `design:check` и сборка проходят, e2e — 90 сценариев с первого прогона (56,1 с).
- `npm test`: 402 unit-теста в 52 файлах прошли (34 новых: 14 — таблица обработчиков, 15 — воркер расчётов, 3 — воркер
  скана, 2 — проверка типов).
- `npm run lint` с `design:check`: без замечаний. `npm run build` (с `tsc --noEmit`): проходит. Размеры чанков:
  интерфейс +43 байта (`send`, `jsonCopy`), воркер расчётов −62 байта, воркер скана −5 байт — договор в сборку
  интерфейса функций ядра не добавил.
- e2e: 90 сценариев прошли со второго прогона (54,1 с), без правок ожиданий; первый остановился на подготовке
  `room.setup.ts` («Далее» закрыта — известная гонка фокуса, шаг 6 плана), остальные 89 не запускались.
- Обратная проверка: 18 тестов обоих воркеров проходят и на прежних воркерах со `switch` (коммит `c2b3d2d`, где договоры
  и тесты уже есть, а воркеры прежние; все промежуточные коммиты собираются). Тест таблицы ловит потерю поля:
  с обработчиками без `ppo` у `listenerMap` и `evaluate` и без `goal` у `voiceMap` падают ровно эти 3 случая. Проверка
  `JsonSafe` срабатывает: `Float32Array` во входных данных `modes` даёт ошибку сборки с названием `modes`.
- Приёмка: 1 — копия `computeTypes.test.ts` без пометок даёт ровно 18 ошибок компиляции, каждая по задуманной причине
  (лишнее поле `ppx`, нет `setup`, нет `subId`, `fMax` строкой, неизвестный вид, результат `SetupEval` вместо
  `Heatmap`, прежняя форма `compute<T>`, неполная и лишняя таблица обработчиков, поле `fmax`, обработчик с чужим
  результатом, три случая `JsonSafe`, ответ разбора границ вместо распознавания, разбор без `dims`, поле `unit`,
  единицы `km`); 2 — в `compute.ts`, файлах воркеров и новых модулях слова `any` нет; 3 — `computeHandlers.test.ts`,
  11 случаев; 4 — запись задач приёмом плана на сборках до и после: прямоугольная комната — `listenerMap@#manual`,
  `listenerMap@#tuning/sub`; комната со скосом (волновая модель) — `evaluate@#manual`, `listenerMap@#manual`,
  `evaluate@#tuning/sub`, `listenerMap@#tuning/sub`; последовательности одинаковы, и сами сообщения совпадают целиком,
  кроме случайного `setup.id`, который отличается и между двумя прогонами одной сборки; 5 — сценарии `app`,
  `precision`, `voice-goals`, `scan` в числе 90 прошедших.

Не проверялось: движок Safari (WebKit) и физический iPhone — эмуляция в Chrome их не заменяет. Поведение на устройстве
не должно меняться (сообщения те же), но после обновления приложения стоит открыть расчёты на телефоне.

Замечено, не исправлено:

- `listenerMap` в ручном режиме и в карте автоподбора отправляет лишнее поле `subId` (вид задачи выбирается условием,
  данные общие). Воркер его не читает; оставлено, чтобы не менять сообщения на проводе.
- Ответ воркера по-прежнему не проверяется при выполнении: типы описывают договор, но страница доверяет тому, что
  пришло. При одной версии страницы и воркера (адрес воркера содержит хэш сборки) расхождения быть не может.
