# 047 — Переключатели не выходят за край экрана на 320 px

Статус: реализовано 2026-11-17 (D42), ветка `047-narrow-overflow`. Задачи — [tasks.md](./tasks.md).

## Задача владельца

2026-11-17, после 046, отчёт `github` показал, какие сквозные сценарии падают в WebKit: четыре из пяти упавших — на
проверке, что страница не шире окна. Владелец согласился разобраться, почему в Safari страница шире экрана, и поручил:
«если решение простое — выбери решение сам, закончишь, протестируй, если надо, и запушь». Задача закрывает пункт
отложенного «„Расстановка“ на 320 px шире экрана» (045) и часть пункта о сбоях WebKit.

## Что было до 047 (сверено 2026-11-17, коммит `d7d270e`)

- В CI упали в WebKit (`43969792475`): `navigation.spec.ts` «workspace fits small iPhone…», `precision.spec.ts`,
  `room-controls.spec.ts` «wall picker…», `smoothing.spec.ts` «smoothing changes only the curve…», `voice-goals.spec.ts`
  «room recommendations and best facing…». Локально (Playwright WebKit под Windows) падают те же пять, все на
  `scrollWidth <= innerWidth`.
- Переполнение настоящее и одинаковое в обоих движках. Кнопки `.segmented` — `flex: 1` с наименьшей шириной по
  содержимому, без переноса. На 320 px:
  - «Точность расчёта» («Стандартная» 107,9 + «Высокая» 76,3 + «Максимальная» 122,1 px с промежутками и полями —
    318 px при ширине переключателя 254 px): «Максимальная» выходит за край экрана на 29–30 px — «Расстановка»
    (оба режима) и «Голос»;
  - выбор стены («Передняя / Задняя / Левая / Правая», 290 px при 254): кнопки выходят за рамку на 34 px, за край
    экрана — на 1,4 px.
  На 393 px переполнения нет.
- Почему проверки в Chrome проходили: в мобильной эмуляции Chrome (`isMobile`) окно раскладки растёт до ширины
  содержимого, `innerWidth` становится 349 — столько же, сколько `scrollWidth`, и сравнение `scrollWidth <= innerWidth`
  верно при переполнении. Растягиваются и закреплённые элементы (нижняя навигация, подложка меню) — отсюда «не
  умещается нижняя навигация („Голос“)» в пункте отложенного 045: это следствие, а не причина. WebKit оставляет
  `innerWidth` 320 и проверку не проходит. `document.documentElement.clientWidth` в обоих движках — 320.

## Требования

- FR-4701: варианты `Segmented`, не помещающиеся в строку, переходят на следующую строку внутри той же рамки
  (`.segmented { flex-wrap: wrap }` в `src/ui/design-system/components.css`). Если все помещаются — вид прежний, кнопки
  равной ширины. Поведение, роли и клавиатура переключателя не меняются; `.segmented--wrap` и `.tabs` — прежние.
- FR-4702: сквозные проверки «страница не шире окна» сравнивают `scrollWidth` с `clientWidth` через общую `fitsWidth`
  (`tests/e2e/helpers.ts`), во всех восьми местах, где раньше сравнивалось с `innerWidth`; допуск 1 px — там же, где был.

## Приёмка

1. На 320 и 393 px ни один из маршрутов «Комната» (обзор, размеры, стены, пол, мебель), «Анализ» (обзор, моды, поле),
   «Настройка» (сабвуфер, эквалайзер, обработка), «Замер», «Расстановка» (оба режима), «Голос», «Отчёт», «Проекты»,
   «Справка», «О приложении» не шире окна — в WebKit и в Chrome, по `clientWidth`.
2. На 320 px «Максимальная» и «Правая» — на второй строке переключателя, внутри рамки; на 393 px — в одну строку, как
   до 047.
3. Проверки ширины с `fitsWidth` падают в Chrome на CSS до 047 (проверка поломкой кода).
4. `npm test`, `npm run lint`, `npm run e2e` (Chrome) проходят; `npm run e2e:safari` (WebKit) — без сбоев проверок
   ширины.

## Не входит

- Нестабильные в WebKit сценарии `app.spec.ts` «UX: найденный вариант…» и «043: подъём низа…» — не переполнение.
- Подбор вариантов по строкам поровну (2 + 2 вместо 3 + 1 у выбора стены): обычный перенос flex.

## Реализация и проверка

- `src/ui/design-system/components.css` — `.segmented { flex-wrap: wrap; }`; `tests/e2e/helpers.ts` — `fitsWidth`;
  проверки в `navigation`, `precision`, `room-controls`, `smoothing`, `voice-goals`, `room-editor`, `design-system` и
  `fits` (helpers) — через неё; `docs/design-system.md` — «Что изменилось в 047».
- Диагностика 2026-11-17: обход маршрутов в WebKit и Chrome на 320 и 393 px, поиск самых глубоких элементов, правый край
  которых за `clientWidth` (скрипт вне репозитория).
- Проверки 2026-11-17 (Windows): `npm test` — 566 в 63 файлах; `npm run lint` с `design:check`; `npm run e2e` (Chrome,
  эмуляция iPhone, со сборкой) — 102 из 102; `npm run e2e:safari` (Playwright WebKit) — 99 прошли, 2 пропущены
  (аудио), 1 упал — «043: подъём низа…» после перезагрузки не находит «Подъём низа» (не переполнение, см. отложенное);
  все пять прежних сбоев проверки ширины прошли. Поломкой кода: с CSS до 047 проверки ширины с `fitsWidth` падают в
  Chrome (4 сценария из 4 выбранных). Снимки WebKit: на 320 px «Максимальная» и «Правая» — второй строкой внутри
  рамки, ширина страницы 320 / 320; на 393 px — одна строка, как до 047.
- Не проверялось: физический iPhone. У Safari на iOS свои поля кнопок по умолчанию, эмуляция их не воспроизводит; при
  переносе они могут изменить число строк переключателя, но вариант шире строки не получится (самый длинный —
  «Максимальная», около 122 px при строке 246 px).
